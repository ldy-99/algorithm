# 프로그래머스 Lv.3 — 불량 사용자 회고

### 1. 문제 접근 및 알고리즘 선택

문제의 제한사항에서 `user_id`의 개수가 최대 8개라는 점을 확인했다.

최악의 경우 모든 사용자 아이디를 순서대로 선택하더라도 최대 경우의 수는 `8! = 40,320`개이므로, 완전탐색으로 충분히 해결할 수 있다고 판단했다.

처음에는 DFS 백트래킹을 고려했지만, 이 문제는 사용자 아이디를 중복 없이 선택하고 불량 사용자 패턴에 순서대로 대응시키는 구조이므로 `itertools.permutations`를 활용하면 더 간결하게 구현할 수 있다고 생각했다.

이에 따라 다음과 같은 풀이를 설계했다.

1. `permutations`로 불량 사용자 패턴 수만큼 사용자 아이디를 선택한다.
2. 선택된 아이디와 각 패턴의 문자열 길이를 비교한다.
3. `*`를 제외한 모든 문자가 같은 위치에서 일치하는지 검사한다.
4. 모든 패턴을 만족하는 경우에만 결과에 추가한다.
5. 중복된 사용자 조합을 제거한 뒤 전체 경우의 수를 반환한다.

### 2. DFS 가지치기와 permutations의 차이

두 방식 모두 가능한 사용자 배정을 탐색하지만, **유효하지 않은 경우를 제거하는 시점에서 차이**가 있다.

**① permutations를 이용한 완전탐색**

`permutations`는 사용자 아이디로 만들 수 있는 순열을 생성한 뒤, 각 순열이 불량 사용자 패턴과 일치하는지 검사한다.

구현이 간단하고 별도의 방문 배열이나 재귀 함수를 작성하지 않아도 된다는 장점이 있다.

다만 불량 사용자 패턴과 일치하지 않는 배정도 순열로 생성된다. 검사 과정에서 불일치가 발견되면 비교를 중단할 수 있지만, 해당 순열 자체의 생성을 막지는 못한다.

**② DFS 백트래킹과 가지치기**

DFS에서는 불량 사용자 패턴을 하나씩 처리하면서 조건을 만족하는 사용자만 선택하도록 설계할 수 있다.

예를 들어 첫 번째 패턴에 사용자 아이디가 일치하지 않는다면, 해당 사용자를 선택하는 탐색 경로는 더 이상 진행하지 않는다.

이를 가지치기(Pruning)라고 한다.

DFS는 조건을 만족하지 않는 경우를 탐색 도중 제거할 수 있으므로, 불필요한 경우의 수를 줄일 수 있다는 장점이 있다.

**③ 두 방법을 비교한 결과**

| 비교 항목 | permutations | DFS 백트래킹 |
|---|---|---|
| 탐색 방식 | 순열 생성 후 검증 | 조건을 확인하며 선택 |
| 구현 복잡도 | 상대적으로 간단 | 재귀 및 방문 관리 필요 |
| 가지치기 | 순열 생성 자체를 줄이기 어려움 | 조건 불일치 시 즉시 탐색 중단 |
| 적합한 상황 | 입력 규모가 작은 경우 | 탐색 공간이 크거나 제약이 강한 경우 |

이번 문제에서는 사용자 아이디가 최대 8개이므로 전체 순열을 생성하더라도 탐색 가능한 범위라고 판단했다.

따라서 가지치기를 통해 탐색량을 줄이는 DFS보다 **구현의 단순성과 가독성을 고려하여 `permutations`를 선택했다.**

다만 입력 규모가 더 크거나 패턴에 따른 제약이 강했다면 DFS 가지치기를 우선 고려했을 것이다.

### 3. frozenset을 사용한 이유

이 문제에서 가장 중요했던 부분은 동일한 사용자 집합을 중복으로 계산하지 않는 것이었다.

예를 들어 다음 두 결과는 순서가 다르지만 동일한 제재 대상 집합이다.

- `("frodo", "crodo")`
- `("crodo", "frodo")`

`permutations`는 선택 순서를 구분하므로 두 결과를 서로 다른 순열로 생성한다.

하지만 문제에서 요구하는 것은 **사용자 배정 순서가 아닌 서로 다른 제재 대상 집합의 개수**다.

이를 해결하기 위해 `frozenset`을 활용했다.

```python
results.add(frozenset(user))
```

`frozenset`은 다음과 같은 특징을 가진다.

- 일반 `set`처럼 원소의 순서를 고려하지 않는다.
- 중복 원소를 허용하지 않는다.
- 불변 객체이므로 생성 후 원소를 수정할 수 없다.
- 해시가 가능하므로 다른 `set`의 원소로 저장할 수 있다.

따라서 동일한 사용자 집합이 여러 순열에서 생성되더라도 결과에는 한 번만 저장된다.

이 과정에서 `set`과 `frozenset`의 차이를 이해하고, 정답에서 중복을 판단하는 기준에 맞는 자료구조를 선택하는 것이 중요하다는 점을 배웠다.

### 4. 구현 과정에서 발생한 문제

초기 구현에서는 각 사용자 아이디가 불량 사용자 패턴과 일치할 때마다 결과를 저장했다.

하지만 문제에서 요구하는 것은 개별 아이디의 일치 여부가 아니라 **선택된 모든 사용자가 각 불량 사용자 패턴을 만족하는 경우의 수**였다.

따라서 개별 비교 결과를 즉시 저장하는 방식에서 벗어나, 하나의 순열에 포함된 모든 사용자가 조건을 만족하는지 먼저 검증하도록 수정했다.

또한 결과를 사용자와 패턴의 쌍으로 저장하는 대신, 선택된 사용자 전체를 `frozenset`으로 변환해 저장했다.

이를 통해 탐색 결과의 유효성 검사와 중복 제거를 분리할 수 있었다.

### 5. 최종 회고 및 배운 점

이번 문제를 통해 세 가지 중요한 점을 배웠다.

**첫째, 입력 크기를 기반으로 알고리즘을 선택해야 한다.**

완전탐색을 무조건 비효율적인 방법으로 판단하기보다, 제한사항을 분석해 실제 탐색 가능한 경우의 수를 계산하는 과정이 중요했다.

**둘째, 같은 완전탐색이라도 탐색 방식에 따른 차이를 이해해야 한다.**

`permutations`는 가능한 배정을 생성한 뒤 검증하는 방식이고, DFS 백트래킹은 조건을 확인하면서 탐색 경로를 확장하거나 중단할 수 있다.

이번에는 입력 크기가 작아 구현이 간단한 `permutations`를 선택했지만, 앞으로는 탐색 공간과 가지치기 가능성을 함께 고려하여 방법을 선택해야겠다고 느꼈다.

**셋째, 탐색 과정의 상태와 최종 정답의 중복 판정 기준을 구분해야 한다.**

탐색 과정에서는 사용자를 각 패턴에 배정하는 순서가 중요하지만, 최종 정답에서는 선택된 사용자의 구성만 중요하다.

이 차이를 해결하기 위해 `frozenset`을 사용했고, 자료구조를 선택할 때 데이터의 특성과 문제의 요구사항을 함께 고려해야 한다는 점을 이해했다.

결과적으로 이번 문제는 단순한 순열 탐색을 넘어, **입력 제한에 따른 알고리즘 선택, 가지치기의 필요성 판단, 중복 상태의 정의, 적절한 자료구조 선택**을 함께 연습할 수 있었던 문제였다.
